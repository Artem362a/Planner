# Правила работы с проектом

- Без явного указания пользователя не подключаться к production и не обращаться к production-сервисам, серверам или базе данных, в том числе для чтения и проверки состояния.
- Любые изменения на production выполнять только с явного разрешения пользователя на соответствующее действие.
- Не выполнять деплой без явного указания или разрешения пользователя.
- Не создавать Git-коммиты без явного указания или разрешения пользователя.
- Разрешение на локальные правки, проверку или запуск проекта не является разрешением на доступ к production, изменения на production, деплой или коммиты.
- Разовое разрешение на действие не считать постоянным разрешением на последующие действия. Например, разрешение скопировать production-базу локально не разрешает изменять production-базу или выполнять деплой.

## Что означает команда выкатить на production

- Явные команды пользователя «выкатывай на прод», «кати на прод», «деплой» и аналогичные означают выполнить штатный деплой через GitHub Actions целиком. Такая команда включает разрешение создать необходимые Git-коммиты с согласованными изменениями и отправить их в `main` для запуска CI/CD. Дополнительное разрешение на эти коммиты и push не требуется.
- Перед отправкой проверить состав релиза, выполнить необходимые локальные проверки и включить исходники, миграции и тесты. Не включать секреты, локальные настройки, дампы БД, демо-данные и временные файлы. Не добавлять посторонние изменения вне согласованного релиза.
- Штатная цепочка: коммит → push/merge в `main` → успешный workflow `CI` → автоматически запущенный workflow `Deploy` для того же коммита → проверка результата.
- Дождаться завершения обеих deploy-джоб: backend на ноуте-сервере и frontend на VDS. Проверить доступность опубликованного сайта и затронутых API/MCP-возможностей. Сам по себе успешный push не означает завершённый деплой.
- При ошибках CI/CD разобраться с причиной и исправить штатный процесс. Не подменять его ручной загрузкой файлов или сборки по SSH. Ручной деплой допускается только по отдельному явному указанию пользователя.
- Просьба объяснить или сохранить схему деплоя сама по себе не является командой начать новый деплой.

## Где что работает

- VDS RUVDS в Москве: nginx, HTTPS, frontend в `/var/www/planner`, серверная сторона туннеля FRP.
- Ноут-сервер: backend FastAPI, PostgreSQL, Telegram-бот, синхронизация расписания и мониторинг в Docker; клиентская сторона туннеля FRP.
- API/MCP: внешний клиент → nginx на VDS → FRP → backend на ноуте → PostgreSQL.
- Backend deploy: резервная копия БД → код коммита успешного CI в `~/Planner` → `docker compose up -d --build` → `alembic upgrade head` → health check.
- Frontend deploy: сборка Vite в GitHub Actions → резервная копия frontend на VDS → публикация сборки и проверка сайта.
- Источник точных команд и настроек: [Deploy workflow](.github/workflows/deploy.yml), [CI workflow](.github/workflows/ci.yml), [RUNBOOK](docs/RUNBOOK.md).
